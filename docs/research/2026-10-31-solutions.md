# Solutions: how each weakness is fixed, and the evidence that the fix works (2026-10-31)

**What this is.** [The deep audit](2026-10-31-framework-deep-audit.md) listed weaknesses. This file gives, for each, one chosen
fix, why the alternatives were rejected, and the evidence, so that what remains to test is a short list of yes/no checks
and not an exploration. Most of the evidence was produced today by running the **pinned core** on this machine.

**Labels.**
- **Proven**: run on the pinned core today, on loopback, with a negative control that failed when it should
  (`testing/spike-carrier/`; re-run it with `README.md`).
- **Source**: read in the pinned source (commit `0b89958`) or in a primary document.
- **Designed**: reasoned from the above; it names the one lab check that settles it.

Loopback has no round-trip time and no loss, and all processes shared one CPU, so every timing below is a lower bound and
every throughput is relative only.

---

## 0. Five facts that changed today, and two corrections

1. **The core we ship cannot do the central idea.** Its build tags have no `with_wireguard`: `primary-core check` answers
   `WireGuard is not included in this build, rebuild with -tags with_wireguard`. *(Proven.)* The module cache of the build
   also held no WireGuard library. ADR-0008 had listed this as an open question; it is not open, it is a required build change (§1.1).
2. **With that one tag added, S1 passes.** A WireGuard session whose socket goes through a Hysteria 2 outbound carried a real
   2 MB transfer without loss. *(Proven.)* The endpoint accepts `detour` and refuses `detour` together with `listen_port`
   (`protocol/wireguard/endpoint.go:60`, *Source*).
3. **S2 passes, with one missing piece found.** Switching the carrier under a live session keeps the open transfer alive in
   one connection. Without a nudge the stall was 12.6 s; with a nudge it was 0.02 s. The negative control (today's shape,
   user streams riding the carrier) was **broken** by killing the carrier: reset after 4,997,120 of 20,000,000 bytes. *(Proven.)*
4. **The TCP fallback carrier (REALITY) carries the same live session**, and the session moves between it and the QUIC
   carrier in both directions, largest stall 0.22 s. *(Proven.)*
5. **A server whose carriers are locked to the session port is not an open relay.** A leaked carrier credential reaches nothing.
   The same server with the hardened exit is validated in one process (§2). *(Proven.)*

**Corrections to the deep audit (applied there).**
- E10 said to give the control API an *empty* cross-origin list. In the pinned source an empty list means **allow all**
  (`experimental/clashapi/server.go:110`). The list must name one origin that can never occur. Measured in §3.1.
- E7 (MTU) is smaller than it looked: Hysteria 2 fragments oversized UDP messages itself (`sing-quic hysteria2/packet.go`,
  `fragUDPMessage`), TCP streams end in the core's own network stack so their packet size never reaches the carrier, and the new
  design carries user traffic as streams. What is left is the AmneziaWG adapter (§7).

## 1. The mechanism, exactly

### 1.1 Build change (required before anything else)

Add `with_wireguard` to the client core's tags, and `with_wireguard` and `with_gvisor` to the **server** core's tags. The server
needs `with_gvisor` because the user-space mode (`system: false`) is behind that tag (`transport/wireguard/device_stack.go`
has `//go:build with_gvisor`, its stub the opposite). Places that list the tags, found by search:

| File | Change |
|---|---|
| `crates/xtask/src/fetch_vendor.rs:107` | add `with_wireguard` |
| `crates/xtask/src/server_cores.rs:28` and its test at `:232` | the server core gets `with_wireguard,with_gvisor`; the test that forbids `gvisor` on the server must be changed on purpose |
| `vendor/primary-core/BUILD-PROVENANCE.md` | regenerated by `fetch-vendor` |
| `docs/architecture/tech-stack.md:87`, `docs/adr/0004-vendored-binary-pins.md` | amendment note (the size also changes: re-measure against the 60 MB installer limit, T115; the spike build is not stripped, so its 63.6 MB means nothing) |
| `THIRD-PARTY-NOTICES.md` | the WireGuard library enters the binary; `lint-branding` keeps its name out of every UI string |

Does not change: the AmneziaWG core, Wintun, the pinned commit, the patch to the tunnel library.

### 1.2 Client configuration shape

A selector `carrier` over the carrier outbounds; a WireGuard endpoint `wg` with `detour: "carrier"`, **no** `listen_port`, and
the server's loopback session port as its peer address (the carrier forwards to it); the routing final goes to `wg`.
The carriers are the Hysteria 2 and REALITY outbounds the project already generates. *(Proven in the harness.)*

### 1.3 Why a switch moves the session *(Source, then Proven)*

The endpoint's socket is created lazily through the detour and re-created whenever it breaks
(`transport/wireguard/client_bind.go`: `connect()` dials again when the previous socket is closed; read and write errors close it).
A selector call `PUT /proxies/carrier` closes **every internal connection** of the group (`common/interrupt/group.go`:
`Interrupt` closes all connections not flagged external, whatever `interrupt_exist_connections` says; that flag only decides
whether *user* streams from the inbound are also closed, and it stays `false`). The endpoint's socket is internal, so it is
closed, re-dialled through the newly selected carrier, and the far end learns the new source from the next authenticated packet.

### 1.4 The missing piece: the nudge

The far end keeps sending to the old path until it receives a valid packet from the new one, and TCP back-off stretches that
wait (12.6 s ≈ 0.2+0.4+0.8+1.6+3.2+6.4 s). **Right after every switch, send small connection attempts through the session
to the measurement origin every 250 ms until one succeeds (at most 5 s).** The service already has the origin address and the
probing code; it costs nothing when idle.

| Variant | Largest stall | Cost |
|---|---|---|
| Nothing (keepalive 5 s) | 12.6 s | none |
| Keepalive 1 s | 1.4 s | a packet every second, for ever |
| **Nudge after the switch** | **0.02 s (planned), about 1 s after the switch (carrier dead; the 3.0 s measured includes 2 s the harness waited)** | none |

### 1.5 The switch procedure (replaces ADR-0008 §3.3's outline)

1. The Conductor decides from measurements (the existing quality and health code).
2. Prepare the standby: the Hysteria 2 client keeps one QUIC connection and reuses it (`sing-quic hysteria2/client.go`: `offer`),
   so a standby that has carried any request is warm. A REALITY standby is a new TCP connection per socket (about three round
   trips; on loopback this was the 0.22 s). *(Source; the warm-up call itself is Designed: a delay test through the standby.)*
3. `PUT /proxies/carrier {"name": X}`.
4. Nudge (§1.4).
5. Verify with the existing probes; retire the old leaf.

Rejected: restarting the core (breaks every stream: the control); the core's automatic `urltest` group (switches without our
measurements and has the same interrupt behaviour; fine as a later safety net, not as the mechanism); a short keepalive
(table above).

### 1.6 Limits, said plainly

- A **server** change is a new session; only carriers are interchangeable under one session. Carriers reduce how often a server
  change is needed; they do not remove it.
- Each switch logs two benign `ERROR` lines in the core (`closed pipe`). The Registry must classify them or the window will
  show a false alarm.
- Throughput (loopback, one CPU, relative): plain Hysteria 2 stream 8.0 s for 300 MB; the session over Hysteria 2 datagrams 15.6 s;
  the session over REALITY **5.3 s**. The QUIC datagram leg is the expensive one. The Conductor's quality score should therefore
  include throughput, not only survival. Whether this matters on a real link is S9: the free server's own cap is 50 Mbit/s and
  its CPU is small (`docs/plans/2026-10-30-guided-onboarding.md` §3), which is exactly where a double layer could bind.

## 2. Server profile v2 (fixes E1, E2, E5, E12; shrinks the attack surface)

**Design.** One core process per server: the Hysteria 2 and REALITY inbounds (carriers) and a WireGuard endpoint in user space,
with these rules by inbound tag (validated by `run.py combined`):

1. Carrier inbounds may forward only UDP to `127.0.0.1:<session port>`; everything else from a carrier is rejected.
2. The endpoint's own traffic: the measurement origin is allowed (a terminal rule), then `resolve`, then `ip_is_private` is rejected.
   `ip_is_private` ("non-public address", since 1.8.0) was tested against loopback, link-local (the cloud metadata address) and
   10.0.0.0/8; the other private ranges are covered by the same predicate but were not each tested.
3. One WireGuard peer **per device**; the device key is the identity.

| What a holder of … can reach | Open (today) | Hardened exit only | Locked carriers | Combined (proposed) |
|---|---|---|---|---|
| a carrier credential: server loopback service, by address | **reached** | refused | refused | refused |
| … by a name that resolves to loopback | **reached** | refused | refused | refused |
| … cloud metadata address, private subnet | dialled (no route on this PC) | refused | refused | refused |
| a device session key: the origin | n/a | n/a | n/a | reached (the one exemption) |
| a device session key: loopback, metadata, names to loopback | n/a | n/a | n/a | **refused (no HTTP answer)** |

*(Proven.)* The combined profile also carried the 20 MB transfer across QUIC→REALITY→QUIC switches in one connection, largest stall 0.22 s.

**Consequences.**
- **E2 is solved structurally.** A leaked carrier credential is worthless on its own; the device key is the identity, one per
  device. Revoking a device = remove its peer and signal the core to reload (`SIGHUP` reloads: `cmd_run.go:197`; a
  blip of about a second for the other devices). *(Source for the reload; the blip is Designed.)*
- **E12.** The exit is user space, so the primary path needs no tunnel device, no IP forwarding and no masquerade rule. The unit can
  run as an unprivileged user with `NoNewPrivileges`, `ProtectSystem=strict` and `ReadWritePaths=/var/lib/dnet`, an empty
  `CapabilityBoundingSet`, `RestrictAddressFamilies=AF_INET AF_INET6 AF_UNIX`, `SystemCallFilter=@system-service`, `PrivateTmp`,
  `ProtectHome` and the kernel-protection switches. Verify with `systemd-analyze security` on the real server; `MemoryDenyWriteExecute`
  must be tried and dropped if the Go runtime objects. A second line of defence that does not depend on the core's rule engine: an
  `iptables -m owner --uid-owner` reject of link-local and private destinations for that user. *(Designed.)* The AmneziaWG unit, if kept as a
  legacy profile, still needs root and forwarding and stays a separate unit.
- **E5.** Replace "add accept rules" with a real inbound default-deny (three ports plus SSH) **with a self-reverting timer** so
  a mistake cannot lock the person out of their own server: apply, wait for the person's confirmation from a second ssh
  session, otherwise revert after five minutes. Enable the distribution's automatic security updates, with a reboot window at a
  fixed quiet hour (a kernel fix needs a reboot; the client reconnects by itself). *(Designed; both use standard tools.)*
- **E13 (new): the server's address.** Oracle's documentation says an ephemeral public address is tied to its private address and is
  deleted with the instance's network interface or when it is terminated; a reserved address belongs to the account until deleted.
  It does not say what a stop and start does. *(Source, with that gap.)* The guide should have the person make the address
  **reserved** (whether the free tier allows one was not found: unverified), and the client should say "the server may have a new
  address" when every carrier to one server fails while the network is otherwise fine. The fix for a changed address is the same
  guided setup, which already produces the endpoint.

Tests that remain: `systemd-analyze security` score, the confirm-or-revert timer, and the throughput of the user-space exit on the real
free shape (S9). All three are on the real server.

## 3. The control surface

### 3.1 The core's control API *(Proven on the pinned build)*

| Check | Result |
|---|---|
| no secret | 401 |
| wrong secret | 401 |
| right secret | 200 |
| right secret, foreign `Host` header (the DNS-rebinding shape) | **200: there is no Host check; the secret is the only protection** |
| cross-origin preflight from a foreign origin, allow-list set to one impossible origin | no allow-origin header: a browser refuses |
| same, allow-list **empty** | **allow-all** (source) |
| secret in the query string on a normal request | 401 (it is accepted only on websocket upgrades) |
| listener | TCP only (`server.go:179`); no unix socket form exists |

**Requirements, each testable:** a random 256-bit secret per run, created by the service and never logged; the service refuses to
start the core if the secret is empty (an empty secret disables authentication entirely: `authentication()`); loopback and a random
port; the allow-list contains one origin that cannot occur; the run directory that holds the config is the restricted one; and, as a
second layer that survives a leaked secret, **a guard rule that lets only `dnetd` connect to that port** (§4: the match is the
program path plus user, which is the same condition the reference guards use).

### 3.2 Changes that redirect traffic need a human the malware cannot imitate (E3)

Rejected first: checking the connecting program's signature (there is no code signing yet, and same-user injection defeats it);
Windows Hello consent (it is not on the secure desktop); a password per request (unusable).

Chosen: **UAC.** Microsoft: the elevation prompt runs on the secure desktop, "only Windows processes can access" it, and an imitation
by malware does not gain elevation. *(Source.)* Design:
1. Add `PendingChange` and `ApproveChange{id}`. A request that changes where traffic goes (add or change an endpoint, a rule that
   bypasses the tunnel, a feed import) is held by the service as pending for ten minutes and shown in the window with the server's
   label and address.
2. `ApproveChange` is accepted only from a client whose token is **elevated** (`TokenElevation`, present in the `windows 0.58`
   crate already in the workspace). The window starts a tiny elevated approver (`dnetctl approve <id>`); no secret travels on a command line.
3. The service records who proposed and who approved, and the window shows the last few.

**Built 2026-11-01 (T160):** the design above, with these differences found while building it. (1) The approver is `dnetctl approve <id>`, which opens its own elevated window; that window shows the change again and needs a typed `yes`, because the Windows prompt names the program and not the server, and there is no option that skips the question. (2) The elevated account may differ from the console user's (a standard user typing an administrator's password), so the service checks the **token's elevation and the session**, not the account. (3) Held: a new server (by hand or by the setup guide), turning a server on, a rule that goes around the tunnel, an imported feed; not held: anything that only tightens. (4) Eight changes at most wait, the same change twice is one, so a flood cannot push out the one a person is reading. (5) **Residual:** on an administrator account at the default prompt level, malware that knows an auto-elevation bypass is not stopped (see ADR-0008 section 12.1); a standard-user account, or the "always notify" level, is the stronger setting.

Everyday actions (connect, disconnect, status) stay unelevated. A standard user is asked for administrator credentials, which is
already the situation at install. Residual: a person who clicks yes to anything; the prompt text is what protects them, so it
names the server. *(Designed; the secure-desktop property is Source.)*

### 3.3 Read-only detail (E4)

Full detail (network names, endpoints, diagnostics) to the console user and administrators; anyone else gets version and a coarse
state. Same file as the authorisation check, already structured for it (`authz.rs`). *(Designed; trivial, testable by the existing
attack-test pattern.)*

## 4. Guard v2: exact design and the five yes/no checks (W6, TunnelVision, ServerIP, the crash gap)

**Lifetimes (Source: Microsoft).** Dynamic objects vanish when the owning process ends, so a guard made of them fails open on a
crash. Persistent objects survive; a persistent object owned by a provider that names a Windows service is applied at start
**only if that service is auto-start**. So: persistent provider, persistent sublayer, persistent filters, provider named after
the `DNetEngine` service. A disabled or uninstalled service lifts the block at the next start, which is the lockout safety.

**Filters (floor taken from the WireGuard-for-Windows rule set, Source):** permit the tunnel adapter by interface; permit the
carrier core by program path **and** user, which also closes the ServerIP gap; permit loopback; DHCPv4 and v6; the five
neighbour-discovery message types; **Hyper-V VM-to-VM** (the lab is Docker and WSL); permit `dnetd` to the control API port
(§3.1); then block everything else, outbound and inbound, IPv4 and IPv6. A block filter wins over any route, so the DHCP-route class
(TunnelVision) is closed without parsing DHCP. The allowed local ranges stay the existing fixed list.

**Calls.** The `windows 0.58` crate already in the workspace exports `FwpmEngineOpen0`, `FwpmProviderAdd0`, `FwpmSubLayerAdd0`,
`FwpmFilterAdd0`, `FwpmGetAppIdFromFileName0`, the persistent and boot-time flags, the provider `serviceName` field, and the app-id
and user-id conditions *(Source: checked in the crate)*. The only change is feature flags, not a new dependency. Use one transaction
per change with a timeout and a retry, because a lock timeout is a published failure of a comparable guard. A periodic check that
the filters are still present covers a third-party firewall removing them.

**Removal paths that need no network:** uninstall deletes the provider and everything under it; `dnetctl guard-release`; a documented
safe-mode command.

**The five checks, each pass or fail, each with its negative control (the guard off must show the leak):**

| # | Check | Pass |
|---|---|---|
| 1 | A rogue DHCP server (a Linux VM on a Hyper-V internal switch running a DHCP server with option 121) | no packet leaves outside the tunnel |
| 2 | Kill `dnetd` | nothing leaves; `dnetd` restarts and the tunnel returns |
| 3 | Reboot with the connection meant to be on | nothing leaves before the service is up |
| 4 | Stop, disable, uninstall the service; run `guard-release` | direct traffic returns each time; the control pipe works throughout |
| 5 | A program other than the core connects to the server address | refused |

Five runs replace exploring.

## 5. The cores run as SYSTEM (new finding, E11)

The service starts both cores as its own LocalSystem children, with no job object, restricted token or process mitigation policy
(searched every crate: none). They parse hostile network input, so a flaw in a core is a flaw with the highest privilege.
Dropping privilege after start is not available: creating the tunnel adapter and changing routes need administrator rights and the
core keeps changing routes on network changes.

Three mitigations, ordered by risk, each a yes/no on one elevated run:
1. **Job object with kill-on-close** for each core (also replaces the orphan scan). Safe; do it.
2. **Forbid child-process creation** for the core (the process creation attribute exists for this). The core should never spawn
   anything; if the tunnel library shells out for routes, the run fails and the bisection ends there.
3. **Prohibit dynamic code**: try last; the build has cgo enabled.

*(Designed.)* Three elevated runs bisect it; no guessing.

## 6. Sleep, resume, shutdown (E9)

The service accepts only Stop and Shutdown (`svc.rs:80`). The `windows-service` 0.7 crate already used supports power events
(suspend, resume, power-setting change), session change, and pre-shutdown. Microsoft-site and forum material says the legacy
suspend messages are not a reliable signal on Modern Standby laptops, and that a service in session 0 should use the user-presence power
setting instead of the display one. *(Source, partly secondary.)* So correctness must not depend on notifications:

1. Accept power events and session change (cheap, covers classic sleep).
2. Register the user-presence/display power settings for Modern Standby.
3. **Ground truth: a tick-gap detector.** The service ticks every second; a tick that arrives far later than scheduled means the
   machine was frozen, whatever the OS said. On a gap or a resume notification: mark every carrier's health stale, keep the guard
   armed, run the nudge and probes before reporting "connected".

Test: suspend and resume a lab VM, and one real laptop once, with the guard on and off. Pass: working tunnel within the failover
target and nothing leaves meanwhile. *(Designed.)*

## 7. IPv6, MTU, logs

- **IPv6 (E8).** Give the tunnel a unique-local IPv6 address next to the IPv4 one: the pinned core accepts it (`check` passed with
  `mtu`, `stack` and a v6 address). User streams are carried as streams, so the family does not matter inside; the server exit
  resolves with `prefer_ipv4`, so a server without v6 fails fast and the application falls back to v4. The guard blocks all v6 outside
  the tunnel. One lab check: an IPv6-only and a dual-stack network, guard on and off. *(Designed.)*
- **MTU (E7).** No action for the new design (see §0). The AmneziaWG adapter's MTU is not set by the project: measure once with
  the existing hostile-network lab if that profile stays.
- **Logs (E6).** `warn` for the client core, plus a test that fails if a log sink is added without redaction.

## 8. Other things found today

- **Upstream security watch.** The core's one published advisory (a 2023 SOCKS-authentication bypass, CVE-2023-43644, fixed before
  1.5.0-rc.5) is far older than the pin, and it concerned the very input type the probe uses. The pin is fine; the *process* is
  missing: a CI job that watches the advisories of the core and of the forks it embeds (the QUIC and network-stack forks, the
  WireGuard library) and fails the build when the pin is affected. *(Source for the advisory; Designed for the job.)*
- **Signing.** SignPath Foundation offers free signing to open-source projects (OSI licence, public repository, signing done from the
  repository's own build, no proprietary component other than system libraries). The vendor-signed Wintun DLL may count as a
  proprietary component; ask them before relying on it. Eligibility is **unverified**. Signing also turns the elevation prompt
  from "unknown publisher" to a named one, which strengthens §3.2.
- **Where the unverified items stop.** Real round-trip times, loss, Windows adapter behaviour, the guard, and the free server's CPU
  are the only things loopback could not show; each is one named check in §9.

## 10. Found while building it (2026-11-01)

Running the composed system (the script's server configuration and the session generator's client configuration, in
two copies of the pinned core, on loopback; `crates/dnetd/src/session_e2e.rs`) found things reading and the spike did not.
Each is now a test.

| # | Finding | Effect | What was done |
|---|---|---|---|
| 1 | **The measurement origin at the server's own session address is unreachable.** The server's user-space network stack owns that address, answers a connection to it itself ("connection refused" from inside the session) and the exit's rules never see it | The session could never be measured | The session origin is its own address, `10.9.0.254`, distinct from the server (`10.9.0.1`) and every device (`10.9.0.2` to `.9`); a test pins the invariant |
| 2 | **The client's built-in rules sent the measurement origin around the tunnel**, for the existing origin too: `10.66.0.1` is inside `10.0.0.0/8`, which stays direct. Found by evaluating the rules, not by running the product | A fetch from the origin would go to the physical network. Every live check and probe through a Hysteria 2 or REALITY tunnel was affected (never run live, so never seen) | Two single-address `Tunnel` rules ahead of the private ranges (`dnet-core::builtin_rules`); a test shows the origins tunnel and their neighbours still bypass |
| 3 | **A first version of my refusal checks proved nothing.** The client's own bypasses (the active endpoint's whole host, private ranges, link-local) sent the probes around the session, and "not reachable" cannot tell a refusal from a request left hanging | A mutation that broke the exit's rule still passed | The client's private bypasses are removed in the test, probes have three outcomes (answered, refused at once, hung), a real service on this machine's private address is the target, and the test checks that service is listening. Mutations of the exit rule and of the carrier lock are each caught |
| 4 | **Loopback is stopped twice.** The server's user-space stack drops a packet addressed to loopback before any rule sees it ("Martian packet dropped"), and the exit's rule refuses it | Defence in depth; the stack's drop shows as silence, not a refusal | The test requires only "never answered" for loopback and "refused at once" for what only the rule can stop (private, link-local, the machine's own LAN address) |
| 5 | **A carrier credential on its own reaches nothing**, shown with a third client that uses the Hysteria 2 carrier directly. With the carrier lock removed it reached the server's loopback origin | Confirms E1 and E2 are closed by the design | In the composed test; the mutation is caught |
| 6 | **The unprivileged account must not own its directory.** Security review: if `dnet` owned `/var/lib/dnet/primary`, a flaw in the core could plant a symlink that the script (root, `cat >`) follows on its next run | Root on the server after a core compromise and a re-run | Root keeps the directory and files (group `dnet`, read only, `750` and `640`); the core needs to create nothing; tests pin it |

**Things decided not to do, with the reason.** (a) *An `iptables` rule by user id* as a second layer under the core's own rules: it cannot be
tested here, and Oracle Linux resolvers sit on a link-local address, so a blanket rule would break name resolution; the proven layers
are the core's rules and the stack's drop. (b) *A default-deny inbound firewall with a self-reverting timer* (E5): the cost of a
mistake is a locked-out owner on a machine they cannot reach, it cannot be tried on a real image from here, and Oracle's own images
already ship a default-deny; the script now says only what it does. It stays open as part of the real-server run. (c) `MemoryDenyWriteExecute`
and `SystemCallFilter` in the core's unit: not verifiable without the real server (`systemd-analyze security`), and a wrong one makes the core
fail to start.

**Not shown by any of this.** Real delay and loss; the Windows tunnel adapter and the guard; the script running as root on a real Linux image
(only its text, its syntax and the configuration it writes are checked); the throughput of the user-space exit on the free server's CPU; and the
REALITY handshake against a real site (here it is forwarded to a local TLS server).
