# Spike S1/S2: a WireGuard session over replaceable carriers (ADR-0008)

Everything runs on loopback. Nothing leaves the machine and no institutional network is involved (Constitution III).
It answers two questions from ADR-0008 §6 with the **pinned core** instead of its documentation:

- **S1.** Can the core carry a WireGuard session over a Hysteria 2 or REALITY outbound?
- **S2.** Does switching the carrier under a live session keep an open transfer alive?

## Build the spike core (the only change from the pin is one build tag)

The shipped core is built **without** `with_wireguard`; it answers `WireGuard is not included in this build, rebuild with
-tags with_wireguard` (checked 2026-10-31 with `primary-core check`). Build the same commit with that tag added:

```bash
git init -q src && cd src && git remote add origin https://github.com/SagerNet/sing-box.git
git fetch -q --depth 1 origin 0b8995879f29a9b98ee027bc17b75e101445b238 && git checkout -q FETCH_HEAD
go build -tags "with_quic,with_utls,with_clash_api,with_gvisor,with_wireguard" -o ../spike-core.exe ./cmd/sing-box
```

Build it somewhere outside this repository. It is a test tool, not a release artifact.

## Run

```bash
SPIKE_CORE=/path/to/spike-core.exe python run.py smoke switch killA plain-killA
SPIKE_CORE=/path/to/spike-core.exe python run.py harden
```

Keys and the certificate are generated by the core into `SPIKE_WORK` (default: a folder in the system temp directory).

## Scenarios and what they showed (2026-10-31, one Windows machine, loopback, one CPU shared by every process)

A transfer of 20,000,000 bytes at 1 MB/s through a SOCKS proxy; two Hysteria 2 servers A and B stand in for two carriers.

| Scenario | What it does | Result |
|---|---|---|
| `smoke` | 2 MB through WireGuard over a Hysteria 2 outbound | all bytes, no stall (S1 passes) |
| `switch` | switch carrier A to B at 5 s and back at 11 s | one connection, all bytes, **largest stall 12.6 s** |
| `switch-nudge` | same, plus small probes through the session right after each switch | one connection, all bytes, **largest stall 0.02 s** |
| `switch-ka1` | same as `switch`, keepalive 1 s instead of 5 s, no probes | one connection, all bytes, largest stall 1.4 s |
| `killA` / `killA-nudge` | kill server A at 5 s, switch to B at 7 s | one connection, all bytes; stall 6.2 s without probes, 3.0 s with (2 s of it is the harness waiting to switch) |
| `plain-killA` (**negative control**, today's shape: user streams ride the carrier) | kill A at 5 s, switch at 7 s | **transfer broken**: reset after 4,997,120 of 20,000,000 bytes |
| `tcp-carrier` | switch QUIC carrier to REALITY over TCP and back | one connection, all bytes, largest stall 0.22 s |
| `*-locked` | carriers may forward only to the session's one UDP port | same results as unlocked |
| `harden` | what a carrier credential can reach: `open`, `hard` (reject private), `locked` | open reaches the server's loopback by address and by name; `hard` and `locked` refuse all of it instantly (`locked` also refuses the origin) |
| `speed-plain`, `speed-wg`, `speed-tcp` | 300 MB unthrottled | 8.0 s plain Hysteria 2 stream, 15.6 s session over Hysteria 2, 5.3 s session over REALITY (relative only: one CPU runs client, three servers and the origin) |

Why `switch` stalls and `switch-nudge` does not: after a switch the far end keeps sending to the old, closed path until
it receives an authenticated packet from the new one (WireGuard roaming), and TCP back-off stretches the wait. Any packet
sent through the session right after the switch ends it.

## What this does not show

Real round-trip times and loss (loopback has none, so handshake costs after a switch are understated), real throughput
(everything shares one CPU), the Windows tunnel adapter and routing (no adapter is created), and the guard.
