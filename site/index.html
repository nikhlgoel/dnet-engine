Keeps a connection up on networks that keep dropping it.

A client for Windows that sends your traffic through a server you run, over whichever connection method works on the network you are on, and keeps going when that network changes. Made for campus, hostel and café networks, first for its author and friends. Anyone is welcome to use it.

Read this first

It is not a bypass tool.

It is not built, offered or described as a way around a network’s rules. What it is follows from what it leaves out:

In one line: it carries your traffic to a server you run, and keeps doing so when the network changes. Nothing more.

  1. It comes with nothing to connect to. No server, no accounts, no shared keys. Without a server you run yourself, it does nothing.
  2. It does not hide that you use a tunnel. The network you are on can still see that a tunnel exists, how much goes through it, and where it ends.
  3. It does not make you anonymous. Your traffic is encrypted to your own server, which sees what any server sees.
  4. It does not promise to get you past a block. It measures what works on a network and says plainly when nothing does.
  5. The rules of your network still apply. A tunnel on a school, work or library network may break them, and what follows is yours to carry. Read the policy first.

The path, and who can see what

  1. Your computerRuns DNet Engine. Your traffic is encrypted here.
  2. Where it can be seenThe network you are onSees a tunnel: that it exists, how much goes through it, where it ends. Not what is inside.
  3. Your serverYours. It decrypts your traffic, so it sees what any server sees.
  4. The internetSees your server’s address, not your computer’s.

What it does

One line each. Open a line for the detail.

Chooses by measuringTries what it has; uses what works.

It tries the connection methods it has against the network you are on and uses the one that works, instead of assuming one is best. Whether a method counts as dependable is also decided by measurement, never by its name.

Follows the networkMoves when the network changes.

When the network under it changes, or a method is blocked, it moves the connection to another path and tells you why, in plain words. When it cannot, it says so.

Fails closedNo quiet “send it direct”.

There is no fallback that sends traffic around a tunnel that is down. (The kill-switch limit below applies: this is a decision made in the service, not yet enforced by the operating system.)

Puts everything backUndoes its changes, even after a crash.

It writes down every change to routes and name servers before making it, and undoes them when it stops or after a crash.

Says whyEvery automatic change has a reason.

Each change comes with a plain-language reason, so “why did it do that?” never needs a log. Anything that is best-effort is labelled best-effort.

Known limits

Three things it cannot promise yet. For each: why, what is being done, and where it stands.

  1. The kill switch is not a guarantee

    Not built yet

    Why
    The service refuses to send traffic unprotected, but nothing at the operating-system level enforces that. A crash or a stopped service does not guarantee that nothing leaves the machine.
    Being done
    A guard made of firewall filters that outlive the service is designed (ADR-0008, task T161). It changes how the machine’s network behaves, so it waits for the owner’s approval and for five yes-or-no checks in a lab.
    Where it stands
    Designed. Not built.

  2. Rules by program are best-effort

    Built, not connected

    Why
    A rule by destination name or address is reliable. A rule by program depends on spotting the program as it connects, which can miss short-lived connections.
    Being done
    The part that watches connections is built and tested, but not yet connected to the service (ADR-0001). The window labels these rules best-effort until it is.
    Where it stands
    Built and tested; not yet connected to the service.

  3. Switching networks can drop open connections

    Not yet measured

    Why
    Today every method is treated as one that drops open transfers when it switches. A method is only called better after a recorded measurement says it survives, never because of its name.
    Being done
    The switch itself is proven on a single computer (tasks T157 and T169). The measurement on two real networks is a lab step that needs a person; its result is then a data file, not a code change.
    Where it stands
    No method has yet been measured to keep an open transfer alive.

Where it stands

Early. The engine runs in a simulated network and a Windows lab; it has not been used on a real network. 15 parts, in three groups. Checked 2026-11-04.

Works 3

In a simulated network and a Windows lab.

  • Background service: three methods, two supervised transport programs, restores network settings
  • Choosing a method by measurement; recovery when one is blocked
  • Command-line client

Built and tested 7

Not yet met a real network.

  • Following the network as it changes (one method; not yet proven on two real networks)
  • Destination rules; noticing a sign-in page in the way
  • Tray icon and window (the icons are placeholders)
  • A guide that makes your own server, in your own cloud account or on any Linux server. It asks for no cloud password or key; the setup script has run only in tests
  • The live map of every part, with its state, how long and why: in the service, the command line and the window’s Activity page
  • Cheap checks while connected: about 1 MB an hour idle, worked out from the code, not yet measured on a wire
  • The leak settings of the tunnel, pinned by tests for all three methods

Not yet 5

Written, planned or waiting for a person.

  • Installer written; not yet built or run on Windows
  • The operating-system kill switch (T161)
  • Rules by program, connected to the service
  • A recorded measurement that a method keeps open transfers alive
  • Networks that have only IPv6 (T166)
